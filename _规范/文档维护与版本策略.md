# 文档维护与版本策略

## 修订记录放在哪

**不建修订历史小节，不用「更新日志」表格。** 每次改动的结论写进提交信息，历史靠 `git log` 查。

理由：文档里的修订表会腐烂——改了正文忘了补表，读者就信了一张过期的表。`git log` 不会忘。

提交信息写法：

```
词条/参与者/势力/矿业联盟：补联盟内部组织结构

- 按「数家矿业巨企＋一座工业枢纽站」写清分工，来源见草稿 26.8.12
- 同步 00-总览/待定项汇总 的条数
```

一条改动一个主题。同一主题跨多个文件时，列清每个文件改了什么。

## 最后更新

只在 `最后更新` 属性里写日期，形如 `2026-11-08`。

- 不改正文就不改日期。
- 纯排版、修错字不算「更新」。
- 语义有变才改。

## 元数据写成属性

元数据一律写在文首的 YAML 属性块里，正文不再写页脚。Obsidian 在属性面板里显示与检索这些字段，`全库索引.base` 也按它们筛选。

```markdown
---
分类:
  - 参与者
  - 势力
  - 联盟
时代:
  - 大灾变前
  - 灾后
  - 环带内战
  - 亚冷战
  - 抗击异魔
状态: 存续（环带内战参战方）
---
```

| 字段 | 写法 |
|------|------|
| 分类 | 列表，一级轴在前，如 `参与者` / `势力` / `联盟` |
| 时代 | 列表，按时间先后排列 |
| 故事线 | 列表，如 `法厄同` / `泰拉` |
| 状态 | 字符串，说清文档现在是什么状态，不用「草稿」「进行中」单独占位 |
| 最后更新 | `2026-11-08` 形式的日期，语义有变才改 |

老文档的页脚已在 2026-11-13 一次性迁入属性，之后不再写页脚；新文档直接写属性块。

## 状态取值

| 取值 | 含义 |
|------|------|
| 现行 | 与设定真相保持一致，可以引用 |
| 存续 | 用于词条实体：这个世界里该实体是否还存在 |
| 待补 | 结构完整但内容有明确缺口；缺口须登记进待办 |
| 存档 | 不再参与现行规则，仅供追溯 |

`待补` 必须在 `待办/` 里有对应条目。没有对应条目的 `待补` 是漏登记，补进待办或改成 `现行`。

## 引用

- 内含引用一律写成 Markdown 链接，不写裸文件名。
- 链到**最具体**的文件：子区已有自己的 `README.md` 时，不要只链到父级。
- 同一段文字里反复引用同一文件时，首次给链接，后文用简称即可。
- 跨库引用（游戏项目的 `Docs/`）写相对路径或仓库地址，不写本机绝对路径。

## 新建文档

1. 先确认没有同类文档。有就改旧的，不新建平行的第二份。
2. 从 [_templates/](../_templates/README.md) 取最接近的骨架。
3. 写完删掉用不上的小节。
4. 在所属目录的 `README.md` 索引里加一行。
5. 若还有缺口，在对应 `待办/` 文件登记。

## 删除文档

1. 先确认没有文档链接到它：全库搜文件名。
2. 把链接改到替代文档，或删掉引用。
3. 删文件，提交信息里写明替代关系。
4. 有叙事价值的旧稿移入 `草稿/`，不进 `词条/`。
